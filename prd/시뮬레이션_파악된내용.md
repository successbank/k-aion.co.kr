## 3. 발견된 이슈

### [Critical] SIM-C1. 프론트엔드 `CommissionRateCompareTab.tsx` 전체가 구 6종 체계 하드코딩
- **현상**: 277줄 전체가 `SALES/SALES_MANAGEMENT/LICENSE/LICENSE_MANAGEMENT/SHARING/BRANCH_OPERATION` 설명 카드 표시. 백엔드는 신 2종만 반환 → 사용자는 존재하지 않는 보너스 유형의 설명을 보고 있음.
- **영향**: 시뮬레이터 화면 접속자가 현행 체계를 오해. 보상플랜 인수 테스트 시 100% 실패.
- **위치**: `/data/successbank/projects/kaion/apps/frontend/src/app/admin/bonus-simulator/components/CommissionRateCompareTab.tsx` line 196–273
- **해결**: Stage 2에서 제품별 매트릭스(5제품 × 4등급) 표로 재설계

### [Critical] SIM-C2. `SaleSimulationTab.tsx` `bonusTypeLabels` 구 라벨 잔재
- **현상**: line 62–69의 `bonusTypeLabels` 객체가 구 6종 라벨만 보유 (SALES/SALES_MANAGEMENT/LICENSE/...). 백엔드가 `SALES_COMMISSION`이라는 키를 반환하면 label lookup 실패 → 빈 라벨 렌더링.
- **영향**: 시뮬 실행 결과에서 "본인 수수료"의 라벨이 "undefined" 또는 공백.
- **위치**: `/data/successbank/projects/kaion/apps/frontend/src/app/admin/bonus-simulator/components/SaleSimulationTab.tsx` line 62–69
- **해결**: Stage 2에서 `{ SALES_COMMISSION: '판매 수수료', EDUCATION_MANAGEMENT: '교육 관리 수수료' }`로 교체

### [Critical] SIM-C3. `prisma/seed-commission-rates.ts` 컴파일 불가 / 실행 불가
- **현상**: `BonusType.SALES/SALES_MANAGEMENT/LICENSE/LICENSE_MANAGEMENT/SHARING/BRANCH_OPERATION` + `MemberGrade.MEMBER/AGENT/MANAGER/BRANCH_CHIEF/DIVISION_CHIEF` — 현재 schema에 존재하지 않는 enum 값 참조. `CommissionRate` 모델 자체가 현재 schema와 부합하는지 여부도 미확인 (매트릭스는 `ProductCommissionRate`로 이전됨).
- **영향**: 시드 재실행 불가 → 신규 개발환경 구축 시 수당률 테이블 빈 상태. 시뮬레이터 매트릭스 검증도 빈 데이터로 실행 → Stage 2 검증 블록.
- **위치**: `/data/successbank/projects/kaion/apps/backend/prisma/seed-commission-rates.ts`
- **해결**: Stage 2에서 `ProductCommissionRate` 기반 신규 시드로 재작성 OR 폐기 후 `.legacy` 디렉터리로 이동

### [Critical] SIM-C4. Bonus 계산의 upline 트리 **비일관성** (sponsor vs recommender)
- **현상**:
  - `BonusCalculatorService.processSaleBonusesInTx()` — **sponsor 기준** (line 227 `getUpline(..., 'sponsor')`)

## 5. 향후 개발 참조 사실

### 5.1 핵심 규칙

1. **`BonusSimulatorService`는 DB를 쓰지 않는다** — 순수 조회 기반. Stage 2의 매트릭스 검증 + Stage 4의 회귀 시뮬에서 **안심하고 반복 호출 가능**
2. **`BonusCalculatorService.processSaleBonusesInTx()`는 트랜잭션 내 원자성** — 판매/재고/PV/보너스가 한 번에 성공 또는 전부 롤백. 시뮬 시 트랜잭션 컨텍스트 외에서 호출 금지
3. **weekCode 3종 구현 독립 주의** (SIM-H5) — 판매/보너스/정산의 weekCode 포맷 차이
4. **upline 트리 이중 구현** (SIM-C4) — sponsor vs recommender. **코드베이스의 "보너스는 recommenderId, 승급은 sponsorId" 문구는 현재 시대차**. 실제 코드는 **둘 다 sponsor로 수렴 중** (bonus-calculator), 시뮬레이터만 recommender에 남아있음
5. **promotion 단일 단계** — `promoteIfEligible()`은 한 번에 한 계단만. 다단계 승급 필요 시 반복 호출 필수
6. **IntegrityCheck 자동 수정은 비파괴적** — sponsorId를 null로 "해제"할 뿐, 회원 레코드 삭제 없음. teamLine도 함께 null
7. **SettlementsService.updateStatus()는 유효성 검사 없음** (SIM-M1) — 관리자 의도로만 사용

## 6. 다른 팀과의 의존

### 6.1 이 영역이 의존하는 팀/모듈

| 대상 | 이유 |
|------|------|
| **개발2팀 (수당 체인)** | `BonusCalculatorService`, `SalesService`, `BonusesService`, `SettlementsService`, `SettlementScheduleService`, `settlement-scheduler.task.ts` 모두 개발2팀 영역 — 시뮬레이션의 검증 대상 |
| **개발1팀 (members/promotion/genealogy)** | `PromotionService`, `GenealogyService`, `IntegrityCheckService`, `MembersService.accumulatePvInTx()` — 승급/정합성/트리 시뮬의 모든 입력원 |
| **기획설계팀** | `.taskmaster/docs/commission-prd.md`, `prd.md`, `members/README.md` — 시뮬 시나리오 작성의 기준 문서 (단, 현재 시대차 상태) |
| **디자인팀 (프론트)** | `bonus-simulator/page.tsx`, `integrity-check/page.tsx` — 시뮬 결과의 수동 확인 화면 |
| **QA팀** | Stage 4 합격 기준의 "자동 테스트 통과" 증거 파일 — `.spec.ts` 작성은 QA와 개발팀 협업 |
| **모니터링팀** | `IntegritySchedulerService`의 Slack 알림 — 운영 시 모니터링팀이 수신 |

### 6.2 이 영역에 의존하는 팀/모듈

| 대상 | 이유 |
|------|------|
| **PM팀 박준혁 (품질PM)** | Stage 4 검증 게이트에서 시뮬레이션 결과를 합격 증거로 활용 |
| **PM팀 강민호 (리더)** | Stage 2 nuance 3개 결정, SIM-C4 upline 비일관성 결정, `.bak`/`seed-commission-rates` 폐기 결정 — 모두 시뮬팀 리포트가 근거 |
| **개발2팀 최민정 (비즈니스 로직)** | 시뮬레이션 결과를 받아 버그 수정 (정유라 → 박준혁 → 최민정 체인) |
| **개발2팀 양현수 (DB 마이그레이션)** | 박선영의 정합성 검증 결과 수신 |
| **개발1팀 김태현 (백엔드 리드)** | 수당 체인의 단위/통합 검증 결과 수신 (Stage 4) |
| **자동화 (이준서 → 개발3팀)** | Stage 4에서 시뮬 스크립트를 GitHub Actions에 연동 요청 |

### 6.3 협업 체인 (Stage 2~4)

```
개발2팀 (수당 체인 수정)
   ↓ 수정 통지
시뮬레이션팀 (정유라)
   ↓ 시나리오 재실행
시뮬레이션팀 (한승민 총괄)
   ↓ 결과 종합
PM팀 박준혁 (품질)
   ↓ 합격/재시도 판정
PM팀 강민호 (리더)
   ↓ 최종 인수
```

### 6.4 QA팀과의 분담 선

- **QA팀**: 자동 테스트 케이스 작성 (`.spec.ts`), 기능 단위 테스트
- **시뮬팀**: 비즈니스 플로우 전체 시나리오, 데이터 정합성, 부하 시뮬, 회귀 자동화
- **겹치는 영역**: 시뮬 시나리오 S-01~S-10 중 일부는 `.spec.ts` 형태로도 작성 가능 → Stage 3에서 김정훈(QA 리드) + 이준서(자동화) 협의 필수
